### 已告知但未自查的概念（知道即可，别当已掌握）

- **三层 Evaluation 区分**：Execution Evaluation（有没有做）/ Task Evaluation（子任务完不完成）/ Goal-Outcome Evaluation（目标达没达成）
- **Executor ≠ Evaluator**：同一 Agent 自执行、自判断、自宣布成功，可靠性会显著下降
- **RAG Debug 七层**：Data → Chunking → Indexing → Retrieval → Reranking → Context Construction → Generation
- **Deterministic Skeleton + Agentic Decisions**：成熟系统不是全交给 LLM，而是确定性骨架控制生命周期/状态/权限/验证，LLM 只处理语义与不确定性判断

## 二、Circle 1 三大洞察【全部已核验】

### 洞察一：契约层稳，语义层漂

9 次真实 LLM 调用中：

- **契约层（validator 管的）完全稳定**：quote 逐字命中 100%（6/6、7/7、4/4…零伪造）；四类必查约束每次都齐；decision_owner 每次都老实写 unknown，未把「采购人员」漂移成选商决策人；confidence 全是 float
- **语义层（LLM 自由发挥的）三次面目全非**：pain_points 条数 7/8/5 且**三次交集 = 0**；desired_outcomes 交集 0；open_questions 交集 0；industry 三次三种措辞

**结论**：`schema 管格式对不对，管不了内容稳不稳`。结构合规靠 validator 锁，语义一致要靠**降温 + prompt 约束抽取粒度**双管，不能指望 validator 兜底。

这是你 Q8 那条 L4 判断（Deterministic Skeleton + Agentic Decisions）的实测验证——你用 pydantic 搭的确定性骨架真的把该锁的锁死了，但**笼子没盖顶**。

### 洞察二：A/B 显示「无差异」有两种解释

你设了 `temperature=0`，跑两次，pain_points 交集仍是 0。看似「降温没用」。

**真相**：DeepSeek 官方文档明确——**思考模式下 temperature / top_p / presence_penalty / frequency_penalty 全部不生效**，设了也被静默忽略。你拧了一个没接上线的旋钮。

识破方式：`reasoning_tokens` 仍是 3084 / 2780 → 说明思考还开着。

**可迁移教训**：

> A/B 实验显示「无差异」时，先排除 (b)「变量根本没被应用」，再下 (a)「变量不影响结果」的结论。做对照实验前，先找一个能反映该变量是否生效的**旁证指标**。

### 洞察三：对抗测试要打最弱的一环

你做了两次注入：删信息（「采购人员」→「相关人员」）、喂假信息（加「张经理希望自动推荐最便宜的供应商」）。**两次都扛住了**：

- 零幻觉引用，所有 explicit 的 quote 逐字落在原话里
- decision_owner 守住 unknown，并把「张经理」精确区分为**需求提出者**而非决策人
- confidence 中位数随模糊降至 0.4，没被诱导抬高

但这不是合格的成功，因为**你攻击的是证据层——那恰恰是系统最坚固的地方**（R1 + 反例 + validator 焊死了）。真正的弱点在语义层，而语义层要用「同输入多次跑看漂移」测，不是用注入测。

**可迁移教训**：设计对抗测试前先问「我在攻击系统最弱的一环吗」，否则测得再多只是确认已知。

## 三、四组消融实验【核心数据资产，已全部机械核验】

同一输入，量级痛点 =「每天需处理大量供应商报价单」能否被抽为 explicit pain_point。

| 组 | 配置 | completion 均值 | 量级痛点召回 | pain_points 交集 |
| --- | --- | --- | --- | --- |
| **A** ×3 | 思考开 + 温度默认 | 4478 | **3/3 ✅** | 0 |
| **B** ×2 | 思考开 + temp0（**被静默忽略，无效**） | 3930 | 2/2 | 0 |
| **C** ×2 | 思考关 + temp0（生效） | **902** | **0/2 ❌** | **3（完全一致）** |
| **D** ×2 | 思考关 + 温度默认 | 1072 | **2/2 ✅** | 0 |

### 三项归因，互相独立

**1. token 下降几乎全部来自关思考。**
A→D 单靠关思考降 **76.1%**（4478→1072）；D→C 再加 temp0 仅降 15.9%（1072→902），而 B 组两次（4209/3652）实测出的**运行间噪声下限约 14.2%** → temp0 的贡献落在噪声内，n=2 下不可区分。

> 所以「token 减少与温度无关」这个断言**成立**，但正确理由不是「温度不影响 token」，而是「其影响量级低于噪声下限」。这个说法严谨得多，经得起追问。

**2. 一致性提升来自 temperature 真生效。**
只有 C 组交集 = 3。D（思考关但温度默认）交集仍 = 0，B（temp0 无效）交集 = 0 → **关思考对一致性毫无帮助**。

**3. 召回率下降来自 temperature=0，不是关思考。**
D 组关思考但保留默认温度，召回 **2/2 恢复**。这是 D 组的核心价值——没有它，归因只能靠猜。

### D 组是意外发现：它可能才是最优配置

| | C 组（思考关+temp0） | D 组（思考关+温度默认） |
| --- | --- | --- |
| 省 token | 80% | 76% |
| 输出一致性 | 完全一致 | 不稳定（交集 0） |
| 召回 | **静默丢客户明说的事实** | 2/2 保住 |
| 失败模式 | **不可感知** | 可见的方差 |

用你自己 Q1 写下的原则推：**「可感知的失败优于静默失败」→ C 比 D 危险，抽取场景应选 D。**

C 组每次输出都一模一样、都通过校验、都很「稳定」，而客户说的量级痛点从来没进去过——量级恰恰是决定「单机脚本 vs 队列批处理」、决定 AI 成本 ROI 正不正的那条信息。

> 这是你 Q1 的抽象原则第一次能反过来指导具体配置选择。这层闭环你自己还没走一遍。

### 一个待解释的异常

D 组两次输出的 pain_points **全是 explicit（4/4、5/5），零 inferred**；A 组 inferred 约占 35%。关思考 + 默认温度下模型停止推断了。利弊待判：没有臆测了，但也没有增值分析（A 组那条 inferred/0.8「格式不统一导致抽取对齐困难」是有价值的洞察，D 组给不出）。

## 四、工程实现要点

### schema.py 的三处强制（把教训变成结构）

| 你犯的错 | 对策 |
| --- | --- |
| 没分事实/推断 | `SourcedClaim`：`source` + `quote`（explicit 必填，须逐字存在）+ `confidence`（inferred 必填，0~1） |
| Constraints 整类缺失 | `check_minimum_coverage` 强制 deployment / data_sensitivity / volume / integration 四类 |
| 低置信度推断冒充客户诉求 | `check_no_inferred_leaked_as_explicit`：confidence < 0.5 不许进 desired_outcomes |
| 字段被静默丢弃 | `model_config = ConfigDict(extra="forbid")`，三个类**都要加**（平级类不继承 model_config） |

### prompt 四段式（顺序不能换）

**角色 → 输出格式 → 规则 R1–R7 → 反例**

- R1–R7 每条都对应你踩过的具体坑，不是通用最佳实践
- **反例段是质量杠杆**：模型对「不要做 X」的理解远不如「X 长这样，别这样」。三个反例全部摘自你自己的答卷
- 字段清单**手写**，不要用 `model_json_schema()` 自动导出（5008 字符，且会把教学注释一起喂给模型）
- **样例必须用占位符**（`<客户原话中逐字存在的片段>`），不能填真实内容——否则测出来的是复读能力，不是抽取能力

### prompt / validator 的分工原则

> **validator 拦得住的，prompt 一行带过**（漏了会被拦下并带错误信息重试，reflexion 兜住）；
> **validator 拦不住的，prompt 必须配反例重点写**（纯语义判断，代码查不了）。

拦不住的典型：R1 的「quote 必须逐字存在」、volume 的「quote 真但 value 越界」、R6 三执行主体、R7 待澄清纪律。

### 你发现的 schema 漏洞（尚未修）

`check_evidence` 只验证「explicit 有没有 quote」，**不验证 value 的内容是否真来自那段 quote**。所以可以标着 explicit、附上真 quote，却在 value 里夹带推断——schema 拦不住。这是「把推断提升为事实」的隐蔽变体。

**修法方向**：没法靠纯规则判断，得靠一次额外 LLM 调用核对 value 与 quote 的蕴含关系 → **你的 Evaluator 自己也需要是个 LLM**。这跟 D2P 里 pixelmatch 那种纯确定性校验是不同性质的问题。

另：`data_assets`、`current_workflow`、`decision_owner`、`automation_boundary` 四个字段都**没有证据约束**，而你的漂移全部集中在这几个字段。带 source/quote 的地方你没出错，没带的地方一路漂移——**没有结构强制的地方，人会自动用「觉得合理」的东西填空**。

## 五、两个项目的核实结论【已读代码核验】

### 三项不成立（面试会被打穿，别再这么说）

1. **「Figma → Website → Deploy」的 Deploy 不存在**：`deployment-adapters/src/index.ts:4` 硬编码 `DeploymentMode = 'dry-run'`，`hostingPlatformBuilt: false`，rollback 返回 `status: 'skipped'`，无任何云平台 SDK / CI 配置 / 部署 URL
2. **D2P 零原生 LLM 调用**：`packages/` 下 grep `openai|anthropic|llm|chatCompletion` 零匹配，LLM 能力全由外部 Codex Runtime 在交互会话中提供
3. **D2P 零 Python**，纯 TypeScript。而 88% 目标岗位要求 Python

### 两项你严重低估了

1. **AEOS 的校验器是真代码**：`docs/scripts/usecases-lint.sh` 230 行 bash，实现 C1-C8 八项机械校验（模糊断言、统计自洽、TC-ID 唯一、失败模型覆盖），退出码区分 ERROR/WARN 并作为门禁；另有 `automation-index-lint.py`、`pack-contract-lint.sh`、`state-view-lint.sh`。**你在 Q12 说的「不能让执行 Agent 自己宣布成功，要独立 Evaluator 基于 Evidence 判断」——你写过。**
2. **D2P 有量化验证闭环和硬指标**：Evidence 是 `pixelmatch` 像素级截图对比（确定性规则，非模型打分）；Evaluation 是 8 个 phase gate 逐一检查数值阈值（`visual-refinement-loop.ts:351`）；experiment-01 的 mismatch ratio **从 0.456 迭代约 10 轮压到 0.00924**（阈值 0.01）。另有 49 个实质测试文件、真实 Figma REST API 集成（含 retry 与 asset export）

### 统一诊断

> **两个项目是同一个形状：验证层很强，生成层为零。你建了裁判，没建选手。**

确定性校验、量化阈值、像素级证据、phase gate、门禁退出码——扎实且罕见。但原生 LLM 调用、structured output 解析、代码级 agent loop、Python AI 栈，全部为零。两个项目都没有自主循环：AEOS 的重试/流转写在 prompt 里靠 LLM 自觉，D2P 的 Acceptance 是人工 gate（daily-runner 只产出 handoff JSON，不触发下一轮）。

这也解释了 ChatGPT 给的那些 L4 为什么**既真又虚**：设计和表达层面确实到了 L4，但实现层面从未被代码强制过。

## 七、能力画像

### 强项（可当差异化标签）

- **Workflow / Agentic Workflow / Structured Output：L4**，且是自主推导（从「LLM 概率性 / Runtime 确定性」推出「需要 Contract」），不是背的
- **Context Engineering / Evaluation：L3.5**
- **证据分级与确定性校验**：pixelmatch、C1-C8 lint、phase gate 阈值 —— 这是市场付溢价最高、候选人最稀缺的一块

### 短板

- **LLM Fundamentals：L2**。能讲 Next Token Prediction，但追问 Attention 解决什么、Temperature 为何影响输出即断
- **压缩表达**。Q3 从 250 字五 bullet 压到一句话四个数字，走了五轮
- **领域分解**。Q9 State 漏三类、Q6 RAG Debug 漏两层、Circle 0 的 Solution 层由 ChatGPT 补齐、Circle 1 的 Constraints 整类缺失

### 模式（比单题评定更重要）

把 12 题重排：**控制结构类答得强**（Q8、Q11 自主推导）；**领域分解类答得薄**（Q6、Q9、Circle 0/1 都漏中间层）。

> 你抓得住系统的控制骨架，但容易漏掉中间的**语义层与数据层**。这是分解习惯问题，不是知识量问题——所以再刷概念补不上，只能靠「面对一段真实领域输入做字段分解」这类题训练。

### 贯穿性盲区（Q2 与 Q4 同一病灶，Circle 2 必修）

> **你度量容易度量的东西（一致性、token 数、重试次数），不度量真正重要的东西（信息有没有丢）。**

Q4 你提了三个好指标——同输入多次的结果交集率（一致性）、候选项之间语义相似度尽可能低（去冗余，**这条是你原创的**）、校验失败重试次数足够低（first-pass yield）。但**三个没有一个衡量「对不对 / 全不全」**。

一个永远返回同样 3 条痛点的系统，在这三个指标上全部满分，同时静默丢掉客户明说的事实。**你的指标体系会把 temp0 认证为「更优」配置。**

解法你手里就有：枚举原话中的原子事实作 ground truth，按配置测 explicit 覆盖率——因 explicit 必带 quote 可溯源，**该召回率能被机械核验**，不需要人判。这正是你 pixelmatch / C1-C8 那套能力的直接延伸，你只是还没想到往这儿用。

## 八、面试可直接用的话术（数字全部核过）

**成本优化**：
> 「抽取类场景我做过四组消融：关思考模式使 output token 从 4478 降到 1072，降 76.1%，而 quote 逐字命中率保持 100%、约束覆盖率不变。温度对 token 的影响落在 14.2% 的运行间噪声内，n=2 下不可区分，所以我没有把它算进收益。」

**实验素养**（这条最值钱）：
> 「我第一次做 temperature A/B 时发现毫无效果，没有直接下『降温对这个任务无效』的结论，而是去查 reasoning_tokens，发现思考模式下 DeepSeek 会静默忽略 temperature。我差点把『变量没生效』误判成『变量无效』。」

**可靠性思维**：
> 「我用四组对照拆开了两个变量的独立影响：一致性提升来自温度生效，召回率下降也来自温度生效，而成本下降几乎全部来自关思考。据此我判断生产环境不该用 temp0——它的失败模式是静默丢事实，而保留默认温度的失败模式是可见的方差，后者可感知、可发现。」

**Evidence-first**：
> 「我在两个项目里都把主观判断转成了确定性指标：D2P 用 pixelmatch 把『像不像』变成 mismatch ratio，从 0.456 迭代到 0.00924；AEOS 用 230 行 lint 脚本实现 C1-C8 八项机械校验并作为门禁。」
