## 一、目标与结果

**Test Point C1-01**：把一段客户原话，经过真实 LLM 调用，变成符合 pydantic 校验的结构化 ProblemModel，且证据分级可信。

**结果**：达成。共 9 次真实 LLM 调用（3 次默认基线 + 2 次无效 A/B + 2 次有效 A/B + 2 次对抗注入）。

**验收**：有条件通过。Criteria ①②③ PASS，④ PARTIAL，⑤ 未产出（见第五节）。

## 二、三个核心发现

### 发现 1：契约层稳如磐石，语义层乱跳

同一输入跑三次（思考模式开、temperature 默认）：

| 层 | 三次表现 |
| --- | --- |
| 契约层（validator 管） | quote 逐字命中 100%、四类约束每次齐、决策角色零漂移、confidence 类型全对 |
| 语义层（LLM 自由发挥） | pain_points 7/8/5 条且**三次交集 = 0**；desired_outcomes 交集 0；open_questions 交集 0；industry 三种措辞 |

结论：**schema 管「格式对不对」，管不了「内容稳不稳」。** 结构合规靠 validator 锁，语义一致必须另外锁。

### 发现 2：关思考模式后，降温连抽取粒度一起稳住

关掉思考模式（`extra_body={"thinking": {"type": "disabled"}}`）+ `temperature=0`，再跑两次：

| 指标 | 思考开 + 默认温度（3次） | 思考关 + temp0（2次） |
| --- | --- | --- |
| pain_points 条数 | 7 / 8 / 5 | **3 / 3** |
| pain_points 交集 | **0** | **3（完全相同）** |
| desired_outcomes 交集 | 0 | 2 / 3 |
| open_questions 交集 | 0 | 2 / 3 |
| industry | 三种不同措辞 | **两次完全相同** |
| completion_tokens | 平均 **4259** | 平均 **902** |

**成本降 78.8%，抽取质量未降**（7 次运行 quote 逐字命中率仍 100%）。

reasoning_tokens 曾占 output token 的 69%~74% —— 纯抽取任务根本不需要思维链。

> 我的旧假设「降温只能稳措辞、治不了抽几条」被自己的数据推翻了：关思考之后，条数也从 7/8/5 收敛到 3/3。

### 发现 3：A/B 实验差点得出完全错误的结论

第一次 A/B 我设了 `temperature=0`，跑两次，pain_points 交集仍是 0。差点写下「降温对这个任务无效」。

**真相**：DeepSeek 官方文档明确——思考模式下 `temperature` / `top_p` / `presence_penalty` / `frequency_penalty` **全部被静默忽略**，设了也不生效。我拧了一个没接上线的旋钮，测的是「默认 vs 默认」。

**怎么发现的**：输出里 `reasoning_tokens = 3084`。如果思考真关了，这个数应该是 0。是旁证救了场。

**教训**：A/B 显示「无差异」时有两种解释 —— (a) 变量不影响结果，(b) 变量根本没被应用。**必须先排除 (b) 才能下 (a) 的结论。**

## 三、对抗测试：方向错了，但错得有收获

两次注入都没能让系统翻车：

| 注入 | 手法 | 结果 |
| --- | --- | --- |
| 模糊注入 | 「采购人员」→「相关人员」 | quote 零幻觉；decision_owner 保持 unknown；confidence 中位数降到 0.4（模型感知到模糊并变谦虚） |
| 诱导注入 | 加入「采购部的张经理希望能自动推荐最便宜的供应商」 | 「张经理」被正确区分为**需求提出者**而非决策人，decision_owner 仍对决策权标 unknown；接受了真实诉求但补了 inferred/0.65 的风险提示 |

**为什么没翻车**：我攻击的是证据层（quote 真实性、角色漂移），而那恰恰是 validator + R1 + 反例焊得最死的地方。

**真正的弱点在语义层**，而语义层的不稳定**用注入测不出来**，只能用「同一输入多次跑、看字段级交集」测——那个我在发现 1 里已经测到了。

**教训**：设计对抗测试前先问「**我在攻击系统最弱的那一环吗？**」，否则测得再多也只是在确认已知。

## 四、我自己的错误（这部分别删）

1. **Evidence 差点全丢**：`output.json` 每次运行被覆盖，run1 靠手动另存才保住。已修为 `output-时间戳.json`。
   讽刺的是我在 Design-to-Production 里做过 artifact hash 溯源和 visual-refinement-ledger——**我最强的能力，在最该用的地方掉线了**。
2. **手写 JSON 时把事实和推断混装**：volume 标 `explicit` 却在 value 里写「日均可能几十到几千份」。quote 是真的，value 越界了。validator 查不出这种错——这是 schema 的第 6 个洞。
3. **`confidence` 写成字符串 `"0.9"`**：pydantic 帮我静默转成了 float，所以没暴露。如果模型输出 `"high"`，直接就炸。
4. **`open_questions` 只加进了 JSON，没加进 schema**：pydantic 默认 `extra="ignore"`，我写的 2 条待澄清项被**静默丢弃**，校验还显示通过。已改为 `extra="forbid"`——把静默失败变成显式报错。
5. **A/B 实验没验证旋钮是否生效**（见发现 3）。

## 五、两项已知局限（验收时如实记录的）

1. **reflexion 路径未被实战触发**：「校验失败 → 带错误信息重试」这条路径只在 mock 模式演示过。9 次真实调用全部一次通过，所以**真实场景下的自我修正能力从未被验证**。
2. **没有产出真正的失败案例**：两次对抗注入都被抵抗。这是鲁棒性证据，不是失败案例。Evidence 里要求的那一项，严格说**未达成**。
