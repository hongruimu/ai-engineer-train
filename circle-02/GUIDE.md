# 第一部分 · 目标

## 1.1 本圈练什么

**表层能力**：Context Engineering。
把 Circle 1 产出的结构化 ProblemModel 变成一条检索 query，召回真正相关的 Solution / Capability / 历史案例。
核心函数是 `build_query`。

**里层能力（真正的训练点）**：Evaluation。
判断一个指标有没有判别力——即「这个分数到底在测什么」。

为什么里层才是重点：检索天生自带可量化指标（recall@k / precision@k），
是练"如何不被自己的指标骗"的最佳载体。这也是你目前最大的盲区，已连着撞上三次同一堵墙：

| 场合 | 指标看起来 | 实际 |
| --- | --- | --- |
| 前置题 | 全文档级召回 0.92 | 掩盖了 pain_points 字段级退化（0.75） |
| 本圈主体 | recall@5 = 1.0 满分 | 恒真指标，任何检索器都满分 |
| Circle 1 Q4 | 一致性/去冗余/重试次数三项全优 | 永远返回同样 3 条的系统也全优，同时静默丢事实 |

三次都是「指标很好看，但没测到真正重要的东西」。

## 1.2 为什么顺序必须是"先修装置，再谈策略"

上一轮的消融实验证明了这一点——四个 query 构造策略分数**完全相同**：

```
V0 全字段拼接（774 字）              recall 1.0  precision 0.5  MRR 1.0
V1 剔除 unknown 噪声                recall 1.0  precision 0.5  MRR 1.0
V2 只留 explicit + 高置信度          recall 1.0  precision 0.5  MRR 1.0
V3 极简：只用 scenario+function（6字） recall 1.0  precision 0.5  MRR 1.0
```

连「只用六个字」都等于「774 字全字段拼接」。
这不是说 query 构造不重要，而是**当前装置根本测不出它的好坏**。
在 6 篇语料 + 1 条 golden 上，任何策略差异都被淹没。

所以现在谈 `build_query` 怎么写是浪费时间——写了也无法验证。**装置先修，策略后谈。**

## 1.3 产品位置（别搞错）

本圈对应技术能力变现产品的**匹配层**：
客户问题进来 → 检索出「该卖什么方案」+「谁能做」，是 Problem ↔ Solution ↔ Capability 三层的连接处。

⚠️ Circle 1 你犯过一个错，别重犯：
当时说"报价单量大、格式有 Excel/PDF，所以引入 RAG 做数据管理与检索"——那是误判。
比价环节是**有界文档集上的结构化抽取 + 确定性比较**，向量相似度在那里没有增益。
**检索的合法位置在匹配层，不在业务执行层。**

## 1.4 求职价值

boss 直聘 JD 高频的两条正好是本圈两条腿：
RAG 全链路（切片/召回/重排）+ Eval-Badcase 闭环。
后者是那 34% 薪酬溢价、47 天招不到人的"Agent 稳定性工程"。

面试叙事的差别：

- ❌「我搭了一个 RAG 检索链路，recall 达到 1.0」
- ✅「我发现 recall@5=1.0 是假指标，因为 k 逼近语料规模，于是加了 precision 和防呆断言，之后才谈 query 构造策略」

第二句证明你会做 Evaluation，第一句只证明你会跑代码。

## 1.5 通关判据

本圈完成 = 下面五条全部满足：

1. 语料 ≥ 20 篇，且四类干扰齐全（见 Step 3~6）
2. golden ≥ 15 条，含多正例与零正例负样本查询
3. 消融实验中 V0~V3 分数**能拉开差距**（这是装置有效的证明）
4. 你自己写的 V4 策略在 golden 上稳定优于 V0，且未硬编码答案词
5. Stage 2 向量检索完成，且能用数据说清它比关键词强在哪些查询上

### ⚠️ 关于 BM25 那个公式

第 110 行这个，你现在可能正盯着它：

```python
score += self.idf.get(t, 0.0) * (tf * (self.k1 + 1)) / (tf + denom_norm)
```

**这行你不需要懂。** 需要懂它的人是调 BM25 参数的人，不是做 Context Engineering 的人。

你只需要一句话：**BM25 是加权的词面重叠分数，词越罕见权重越高（IDF），文档越长惩罚越重（b）。**

面试被问到，标准答案就是：「BM25 是 TF-IDF 的改进版，用 k1 控制词频饱和、b 控制文档长度归一化」——背这一句，不用推。

## Phase C · 扩 golden 🎯

> 这是训练点。golden 是唯一的 ground truth 锚点，**必须你手标，不能让模型标**——
> 否则又变成自己验自己，和前置题「无人工 golden set 则 judge 无法校准」同理。

### Step 7 🎯 把现有 Q1 改造成多正例 · 15 min

**问题**：现在 `golden.json` 只有 1 条查询，且 `relevant_doc_ids: ["C1"]` 只有 1 个正例。
单正例时 precision 的上限就是 `1/k`，你看到的 0.5 是天花板值，不是真实水平。

**做什么**：Step 5 已经建了"正例家族"。
回到 Q1，判断除 C1 外，哪几篇**也真正能解决**这个客户的报价单比价问题，把它们加进 `relevant_doc_ids`。

**判断标准（这是你要动脑的地方）**：
不是"词面像"，而是"如果我是客户，这篇方案能不能解决我的问题"。
半相关的（只做解析不做比价）**不该**算正例——它们正是 precision 要惩罚的对象。

**完成判据**：`relevant_doc_ids` 有 2~3 个元素，且你能说出每一个为什么算正例。

---

### Step 8 🎯 加 2 条"零正例"负样本查询 · 20 min

**为什么这是最重要的一步**：真实产品里最常见的失败模式是——
客户问了一个你能力库里**根本没有对应方案**的问题，检索器却硬凑一个最像的返回。

你现在完全没测这个。

**做什么**：往 `golden.json` 加 2 条查询，`relevant_doc_ids: []`（空数组）。
ProblemModel 描述一个你的语料里确实没有解决方案的问题
（比如"帮我们的工厂做设备预测性维护"，如果语料里没有这类方案）。

**⚠️ 先想清楚再写**：现在的 `recall_at_k` 遇到空 `relevant` 会返回 `0.0`
（见 `retrieval.py:213-214`）——**这是错的**。
空正例时"什么都没召回到"才是正确行为，应该得分高而不是 0 分。

**这一步分两层，难度完全不同**：

**(a) 指标层 —— 你已完成 ✅**

`recall_at_k` / `precision_at_k` 的零正例分支已改对，四种状态真值表正确：

| retrieved | relevant | 语义 | recall | precision |
| --- | --- | --- | --- | --- |
| [] | [] | 完美克制 | 1.0 | 1.0 |
| [X] | [] | 硬凑 1 篇垃圾 | 0.0 | 0.0 |
| [X,Y,Z] | [] | 硬凑 3 篇垃圾 | 0.0 | 0.0 |
| [C1,...] | [C1,...] | 正常召回 | 0.6 | 1.0 |

**(b) 检索器层 —— 已实测证伪，不要求你做** ⚠️

原本要求给 `KeywordRetriever` 加弃权能力（`should_abstain`），让它在无关 query 时
返回 `[]`，从而触发上面的完美克制分支。

**2026-09-29 穷举验证：这在 BM25 上无解。** 四种规则的取值区间全部重叠：

```
规则              Q1(该留,5正例)  Q2(该弃)  Q3(该弃)   可行?
A ratio =s1/s2        1.13        1.78      1.04     ❌ 重叠
A gap   =s1-s2       50.51        4.80      0.30     ⚠️ 分离的是 query 长度
B norm1 =s1/ntok      0.39        0.41      0.34     ❌ 重叠（且方向反了）
C rel_mean=s1/mean    1.99        3.69      2.54     ❌ 重叠
D 绝对 s1           429.9        11.0       7.9     ⚠️ 分离的是 query 长度
```

**根本原因**：BM25 度量词面重叠，不是语义相关。Q2 该弃权，但它召回的 F2
是同词面不同领域的干扰文档——词面上 F2 确实高度匹配设备预测性维护，
BM25 给高分是**正确**的。任何对词面分数的单调变换都无法恢复语义相关性。

**所以弃权能力属于 Stage 2**（向量检索 / cross-encoder 重排 / LLM 判定），
不属于关键词基线。`should_abstain` 保留是为 Stage 2 的检索器准备的接口，
关键词检索器的正确取值就是 `abstain=False`。

**完成判据**：
- golden 里有 ≥2 条 `relevant_doc_ids: []` 的查询 ✅
- 零正例的评分逻辑能区分「完美克制」与「硬凑垃圾」 ✅（指标层已做对）
- 跑 `retrieval.py` 不崩溃，且 Q2/Q3 显示 ❌（recall=0.0）——**这是正确的**，
  它如实测量了「BM25 无法弃权」这个真实产品风险，不是待修复的 bug

**关于 focus 的候选集（必读，否则会误解它的性质）**：

检索系统里最值钱、最无法自动化、也最不能外包给模型的一块。**

> 为什么必须你标、不能我标：语料是我写的、查询是我写的，标注再由我写，
> 就变成"自己出题、自己写答案、自己判分"，golden 不是 ground truth 而是我的意图回声。
> 而且"相关性"没有绝对答案——同一篇文档对不同查询角色会反转
> （I1 对 Q1 是纯噪声，对 Q9 客服问题却是标准答案）。这个判断只能你做。

**标注判据只有一个问题**：「如果我是这个客户，这套方案能不能解决我的问题？」

- 能完整解决 → 标为正例
- 只解决一部分（如只做解析不做比价）→ **不标**，它是 precision 该惩罚的对象
- 领域相邻但解决别的问题（如供应商准入 vs 报价比价）→ **不标**
- 语料里确实没有方案能解决 → 标 `[]`（空列表，**不是 null**）

**⚠️ 诚实边界**：这个工具只能降低无意锚定，**挡不住故意作弊**——
`corpus/solutions.json` 就在你机器上，你随时能打开看 role。技术上防不住。

所以 ground truth 的价值最终取决于你的诚实。Step 7 你主动承认「我是看着 role 标的」，
**那一次诚实比标对全部 15 条更有价值**。这次同样：如果标注时你偷看了 role，
就在提交时说明，我会把它标为「非独立标注」而非当作有效证据——就像 Q1 现在这样。

### F.1 本阶段目标

**表层能力**：在本地 Ollama 上运行 embedding 模型，实现一个最小可用的

4. Hybrid 的提升来自失败模式互补，还是只是把两个错误列表混在一起？

### F.2 固定设计，暂时不要扩张

| 决策 | 当前选择 | 原因 |
| --- | --- | --- |
| 本地服务 | Ollama 原生 `/api/embed` | 无云端 key，数据不出本机，协议简单 |
| 正式模型 | `qwen3-embedding:0.6b` | 中文/多语言优先，体积适合作为第一版基线 |
| 已有模型 | `nomic-embed-text:v1.5` | 只用于验证接口链路；不作为中文正式结论 |
| 文档输入 | `Document.text` 原文 | 不在文档侧偷偷加入 metadata 答案 |
| 查询输入 | V4 `v4_your_strategy()` 输出 | 保证 BM25 与 Vector 比较时 query 相同 |
| 相似度 | 点积 | `/api/embed` 返回归一化向量，点积等价于 cosine 排序 |
| 存储 | 先内存，正确后再加 JSON 缓存 | 只有 23 篇，不需要向量数据库 |
| 检索数量 | `top_k=3` | 与关键词基线和 golden 口径一致 |

**刻意排除**：FAISS、Chroma、Milvus、ANN 索引、GPU 调优、LangChain、
模型微调、reranker。它们都不是证明「语义检索是否补上 BM25 失败」的必要条件。

### Step 13.4 🔴 实现 `VectorRetriever` · 已完成

**只做一件事**：根据 query 与文档向量的点积返回 `top_k` 个 `doc_id`。

执行逻辑：

```text
初始化
  → 一次性批量计算 23 篇 Document.text 的向量
  → 保存 doc_id 与向量的对应关系

retrieve(query, top_k)
  → 计算 query 向量
  → 与每篇文档向量做点积
  → 按 (-score, doc_id) 排序
  → 返回前 top_k 个 doc_id
```

实现约束：

- 文档侧只使用 `Document.text`，禁止读取 `metadata.role`
- 同一实例内不得每次查询都重新计算文档向量
- 分数相同时按 `doc_id` 排序，保证结果确定
- 此时不实现弃权；Vector 的零正例问题必须先被真实测量
- 此时不实现缓存、不实现 Hybrid

#### Step 13.5 复盘：从这次实验中应该建立的核心认知

这次实验最有价值的地方，不是得出「Vector 比 BM25 好」或「Vector 不如 BM25」这种
一句话结论，而是暴露了检索系统中五个容易混淆的问题：**标注质量、排序改善、真实退化、
Top-K 容量、弃权能力**。面试中如果能把这五件事拆开说明，会比只背 Recall、Precision、
MRR 的定义更有说服力。

##### 1. Golden 的质量决定了评测结论是否可信

本次复核发现三条错误标注：

| 查询 | 原标注 | 修正后 | 原因 |
| --- | --- | --- | --- |
| Q13 跨境运价比价 | `C1/H1` | `F4` | `C1/H1` 是采购报价单比价；只有 `F4` 覆盖货代运价、附加费、到岸成本和订舱 |
| Q14 集团支出分析 | `E3/B2/C2` | `E3/B2` | `C2` 解决 RFQ 和战略寻源，不能完成跨 ERP 数据汇聚与口径统一 |
| Q15 库存盘点治理 | `B2` | `[]` | `B2` 只提到收货入库，没有盘点、账实核对和库存准确性治理能力 |

错误 golden 会把正确检索判成错误，也会制造不存在的模型提升。修正前，Q13 看起来是
Vector 把 Recall 从 `0.5` 提升到 `1.0`；但当真正正例改为 `F4` 后，BM25 和 Vector 都把
`F4` 排在第 1，所谓改善随即消失。

**面试核心认知**：

> 离线评测指标不是客观真理，而是「检索结果相对于人工标注」的计算结果。
> 如果相关性判据不清楚或 golden 标错，模型优化方向也会被带偏。

标注前必须先明确相关性标准。本实验采用严格标准：

```text
能够完整解决客户问题       → 正例
只提供其中一种能力         → 负例
领域相邻但解决另一个问题   → 负例
语料中没有完整方案         → []
```

##### 2. “改善 0 条”不代表 Vector 没有产生价值

`vector_eval.py` 的改善/退化分类只比较：

```text
Recall@3、Precision@3、Reciprocal Rank
```

只要相关文档没有跨过 Top-3 边界，或者第一篇正例的位置没有变化，指标就可能完全不变。

Q1 是最典型的例子：

```text
文档 C2：BM25 第 9 → Vector 第 5
```

Vector 已经明显提升了行业黑话文档 `C2`，但它仍在 Top-3 外，所以三个指标都看不到这次
变化。类似地，Q14 中 Vector 把更聚焦的 `E3` 从第 2 提升到第 1，但 BM25 第 1 的 `B2`
本来也是正例，因此两边的 RR 都是 `1.0`。

**面试核心认知**：

> Top-K 指标只观察截断点内的结果。离线分析不能只看平均指标，还要看完整排名、
> 正例名次变化和逐查询结果，否则会漏掉“有改善但尚未跨过 K”的情况。

如果希望衡量这类变化，可以补充：

- Recall@5、Recall@10
- 每篇正例的具体 rank
- MAP 或 nDCG
- 进入 Top-K 前还需要提升多少名

##### 3. Q6 是真正的 Vector 退化案例

Q6 的正确答案是 `E2/B2`：

```text
BM25:
1. E2  188.158  正例
2. B2   99.454  正例
3. E1   62.929  负例

Vector:
1. E2   0.817   正例
2. C1   0.597   负例
3. H3   0.567   负例
7. B2   0.498   正例
```

所以：

```text
Recall    1.000 → 0.500
Precision 0.667 → 0.333
RR        1.000 → 1.000
```

RR 没下降，是因为第一名 `E2` 仍然是正例；Recall 和 Precision 下降，是因为第二篇正例
`B2` 掉出了 Top-3。

BM25 能保住 `B2`，是因为查询和文档有非常强的精确词面重合：

```text
采购订单、入库/收货、供应商发票、三单匹配、财务、ERP
```

Vector 没保住 `B2`，主要是**整篇文档单向量导致主题稀释**。`B2` 同时讲预算、寻源、
供应商、招投标、合同、订单、收货、发票、付款、支出分析和审计；“三单匹配”只占全文
很小一部分。整篇压成一个向量后，向量中心更接近“综合采购平台”，而不是“三单匹配”。

`C1/H3/H2` 虽然不是答案，却集中出现采购、供应商、单据、自动处理、校验和差异等概念，
整体语义与查询接近，因此在向量空间里压过了 `B2`。

**面试核心认知**：

> 向量检索不是天然优于关键词检索。精确术语、编号、产品名和局部能力点通常是 BM25
> 的优势；长文档、多主题文档使用单向量表示时，局部相关能力可能被平均掉。

常见改进方向：

1. 按能力或段落切分长文档，而不是整篇只生成一个向量；
2. 为标题、能力列表等高价值字段单独生成向量；
3. 用 BM25 保留“三单匹配”等精确匹配；
4. 用 Hybrid/RRF 合并 BM25 与 Vector 的候选；
5. 候选召回后再用 reranker 判断完整相关性。

##### 4. 行业黑话 C2 被提升，说明 Vector 部分跨越了语义鸿沟

Q1 客户使用的是普通业务表达：

```text
供应商报价单、比较价格和规格、耗时间、容易遗漏、Excel/PDF
```

`C2` 使用的是行业表达：

```text
RFQ、should-cost、TCO、BOM、award、MOQ、Incoterms、SRM
```

结果是：

```text
BM25：C2 第 9，分数 57.878
Vector：C2 第 5，相似度 0.659
```

这说明 Vector 学到了一部分概念关联，例如：

```text
向多家供应商询价     ≈ RFQ / 供应商应标
比较价格与条件       ≈ 核价 / TCO / MOQ / 条款比对
选择供应商           ≈ award 建议
沉淀历史价格         ≈ price benchmark
```

但不能仅凭一次排名就说“模型真正理解了业务”。查询与 `C2` 仍共享采购、供应商、价格等
通用信息，提升可能同时来自领域相似性、少量共同词和真正的语义映射。若要形成更强证据，
应设计控制变量实验：删除双方共享的通用采购词，只保留客户口语与行业术语，再观察排名。

`C2` 没有进入 Top-3 的原因也不是简单的模型失败。Vector 的 Q1 前五名是：

```text
1. C1  0.800
2. H1  0.771
3. H3  0.746
4. H2  0.715
5. C2  0.659
```

这五篇全部是正例。前四篇比 `C2` 更直接地描述报价文件解析、字段抽取、物料对齐、缺失
校验和比价输出；`C2` 的主题更宽，更偏战略寻源和成本分析，所以排在它们之后是合理的。

此外，Q1 一共有 5 篇正例，而 `k=3`，因此 Recall@3 的理论上限就是：

```text
3 / 5 = 0.6
```

无论检索器多好，都不可能在三个位置中放入五篇正例。因此“C2 未进 Top-3”不能和 Q6
的 `B2` 漏召回混为一谈：Q6 的 Top-3 有空位被负例占据，Q1 的 Top-3 已经全是正例。

**面试核心认知**：

> 判断漏召回时，先看 Top-K 是否有容量、前面是否被负例占据。正例很多且 Top-K 已经
> 全是正例时，某篇正例没进入 Top-K 是截断限制，不一定是排序错误。

##### 5. Q2/Q3/Q15 暴露的是弃权问题，不是普通排序问题

这三条查询在当前语料中没有完整解决方案：

```text
Q2  设备预测性维护          → []
Q3  客户需求痛点归纳        → []
Q15 库存盘点与准确性治理    → []
```

但当前检索器仍然返回三篇文档：

```text
Q2 Vector：H3 0.380、E3 0.374、B1 0.339
Q3 Vector：D1 0.459、H2 0.401、B1 0.388
Q15 Vector：E2 0.440、D1 0.425、G1 0.407
```

原因是当前 `VectorRetriever.retrieve()` 只做了四件事：

```text
计算相似度 → 全量排序 → 截取 Top-K → 返回
```

它没有任何“是否足够相关”的判定。最近邻检索永远能找到最近的文档，即使所有文档都不
合格。向量相似度回答的是“谁相对最像”，不是“谁绝对能解决问题”。

这三个错误结果也并非完全随机：

- Q2 没有设备维护方案，只能匹配到含系统、管理、异常分析等宽泛概念的文档；
- Q3 涉及从杂乱纪要中归纳信息，因此靠近知识库问答和文档抽取，但这些方案不能完成需求共识；
- Q15 涉及订单、入库和数据核对，因此靠近三单匹配、知识库和 OCR，但都不能解决循环盘点。

当前数据出现了一个值得继续验证的现象：

```text
零正例查询的最高 Top-1：0.459
有正例查询的最低 Top-1：0.642
```

因此 `0.55` 左右可以作为一个**待验证候选阈值**。但不能直接把它当成最终规则，因为这个
阈值是看完当前开发集后选出来的，可能过拟合。正确流程是冻结阈值，再用新的正例、弱相关
和零正例查询检验误拒绝与误接受。

**面试核心认知**：

> Ranking 和 Abstention 是两个不同问题。检索器能把候选排好，不代表它知道什么时候
> 应该回答“知识库中没有答案”。生产系统通常需要单独的置信度校准、阈值、reranker，
> 或基于证据充分性的答案拒绝机制。

##### 6. 三个指标分别看到了什么，又遗漏了什么

| 指标 | 回答的问题 | 本次实验中的盲区 |
| --- | --- | --- |
| Recall@3 | 应找到的正例有多少进入前三 | 看不到正例在第 4、第 5 还是第 20；多正例时受 K 上限制约 |
| Precision@3 | 返回的前三篇有多少是真的 | 单正例查询即使完美排第 1，Precision@3 也只有 `1/3` |
| Reciprocal Rank | 第一篇正例排得多靠前 | 第一篇正例之后的其他正例全部不计入 |

当前实现中，如果 `retrieved=[]` 且 `relevant=[]`，Recall 和 Precision 会记为 `1.0`；
但 Reciprocal Rank 仍然是 `0.0`。因此 MRR 不适合单独评价零正例查询的弃权质量。

生产评测还应增加：

- `abstention accuracy`：该拒绝时是否真的拒绝；
- `false accept rate`：无答案时是否错误返回结果；
- `false reject rate`：有答案时是否错误弃权；
- coverage：系统愿意回答的查询比例；
- 在不同 coverage 下的准确率或风险曲线。

##### 7. 这次实验对 Hybrid 的真正意义

当前证据不是“Vector 将取代 BM25”，而是：

```text
BM25：擅长精确术语和局部能力点，例如 Q6 的“三单匹配”
Vector：擅长语义改写和行业表达映射，例如把 Q1 的 C2 从第 9 提升到第 5
```

两者的优势不在同一个查询上，因此具备融合价值。后续 RRF 的目标不是简单提高平均分，
而是验证它能否：

1. 保住 BM25 对 Q6 `B2` 的精确召回；
2. 保留 Vector 对 Q1 `C2` 的排名提升；
3. 不把两路的负例同时带入 Top-3；
4. 与独立弃权机制配合处理 Q2/Q3/Q15。

##### 8. 面试中可以使用的完整表达

可以用下面这段话概括本次实验：

> 我先用同一份语料、同一个 query builder 和相同的 Top-K，对 BM25 与本地 embedding
> 检索进行了逐查询评测。实验中我发现，平均指标会掩盖两类重要现象：一类是向量检索
> 把行业术语文档从第 9 提升到第 5，但因为没有跨过 Top-3，所以指标显示持平；另一类是
> 长文档单向量造成局部能力稀释，使包含“三单匹配”的综合采购平台从第 2 掉到第 7。
> 我还发现最初的 golden 存在错误，导致 Q13 出现虚假提升，因此重新按照“必须完整解决
> 问题”的标准修正了三条标注。最终结论不是 Vector 全面优于 BM25，而是两者失败模式
> 互补：BM25 更擅长精确术语，Vector 更擅长语义改写；同时两者都没有解决无答案查询的
> 弃权问题。所以后续应使用 Hybrid/RRF 做候选融合，再单独增加阈值校准或 reranker，
> 而不是只比较一个平均 Recall。

如果面试官继续追问“你从这个实验里最大的收获是什么”，可以回答：

> 最大收获是检索效果不能只归因于模型。Golden 是否正确、文档如何切分、Top-K 是否有
> 容量、指标是否观察到名次变化、系统是否支持弃权，都会改变最终结论。一个可靠的检索
> 实验必须先保证标注和评测口径可信，再讨论模型优劣。

### Step 13.6 🔧 文档向量缓存 · 已完成

**本步目标**：避免每次创建 `VectorRetriever` 都重新请求 Ollama 计算全部文档向量。
查询向量仍然实时计算，因为每次输入的 query 不同；只缓存变化频率低的文档向量。

**本步不改变**：query builder、相似度算法、排序规则、Top-K 和评测口径。
因此加入缓存前后的检索结果必须完全一致，变化的只能是初始化耗时和 Ollama 请求量。

#### 原子步骤

1. 为每篇文档计算 `SHA-256(Document.text)`，作为内容版本标识；
2. 从 JSON 缓存读取模型名、`doc_id`、文本摘要和向量；
3. 模型名和文本摘要都一致时，直接复用该文档向量；
4. 只把缓存缺失或文本变化的文档批量发送给 Ollama；
5. 用最新 23 篇文档覆盖写回缓存，自动删除已经不在语料中的旧文档；
6. 使用临时文件加原子替换，避免进程中断留下半份 JSON；
7. 验证首次运行、完全命中、单文档变化、模型变化四种情况。

#### 代码阅读级别

**🔴 必须逐行读懂**：

- 文本摘要为什么参与 cache key；
- `_load_or_create_doc_vectors()` 如何区分命中和失效；
- 为什么只批量计算 missing documents，而不是重新计算全部文档；
- 模型名变化为什么会让整份缓存失效。

**🟡 理解协议和效果即可**：

- `hashlib.sha256()` 如何把文本变成稳定摘要；
- `Path.replace()` 如何用临时文件原子替换正式缓存文件；
- JSON 序列化与反序列化细节。

**⚪ 本步不用深入**：

- Ollama 内部如何计算 embedding；
- 操作系统页缓存和文件系统原子写的底层实现；
- 向量数据库、ANN 索引和分布式缓存。


### Step 14.1 🔴 实现 `HybridRetriever` · 已完成

**本步目标**：用 RRF（Reciprocal Rank Fusion）融合 BM25 与 Vector 的排名，利用两路检索
不同的优势，同时避免直接混加量纲完全不同的 BM25 分数和 cosine 相似度。

使用 RRF 融合 BM25 与 Vector 的排名：

```text
RRF(doc) = Σ 1 / (60 + rank)
```

约束：

- 两路先各取大于最终 `top_k` 的候选，例如各取 10 篇
- `rank` 从 1 开始
- 同一文档在两路都靠前时分数累加
- 最终按 `(-rrf_score, doc_id)` 排序并返回前 3 篇
- 不直接相加 BM25 分数与 cosine 分数，两者量纲不同

#### 原子步骤

1. 在构造函数中分别创建 `KeywordRetriever` 和 `VectorRetriever`；
2. 保存候选池大小 `candidate_k=10` 和 RRF 常数 `rank_constant=60`；
3. 每次查询时让两路分别返回前 10 篇候选；
4. 使用从 1 开始的排名计算 `1 / (rank_constant + rank)`；
5. 同一文档出现在两路时累加两次贡献；
6. 按 `(-rrf_score, doc_id)` 做确定性排序；
7. 只返回最终 `top_k` 个文档 ID；
8. 用可控假检索结果验证 RRF 计算，不在本步讨论完整评测结论。

#### 代码阅读级别

**🔴 必须逐行读懂**：

- 为什么融合的是 rank，而不是 BM25 score 与 cosine score；
- `enumerate(..., start=1)` 为什么必须从 1 开始；
- 同一文档为什么要在两路结果中累加；
- 为什么候选池要大于最终 `top_k`；
- 排序键 `(-rrf_score, doc_id)` 如何保证分数降序和结果稳定。

**🟡 理解协议和效果即可**：

- `KeywordRetriever` 和 `VectorRetriever` 的内部打分公式；
- `rank_constant=60` 对头部排名差距的平滑作用；
- 文档向量缓存仍由内部的 `VectorRetriever` 负责。

**⚪ 本步不用深入**：

- 学习式融合、cross-encoder reranker；
- 为每路检索器训练动态权重；
- 大规模向量数据库中的并行召回。

**完成判据**：

```text
两路候选均参与融合
共同出现的文档获得两路分数之和
候选顺序改变时 RRF 排名按公式变化
相同分数时按 doc_id 稳定排序
top_k<=0 或空语料时返回 []
```

2026-09-30 验证结果：

```text
RRF 公式测试           → 通过
两路共同文档分数累加   → 通过
同分时按 doc_id 排序   → 通过
两路候选数量           → 各取 10 篇
top_k=0                → 返回 []
Python 语法检查         → 通过
```

真实 Ollama 冒烟测试使用 Q6：

```text

expected：['E2', 'B2']
Hybrid Top-3：['E2', 'H2', 'B2']
```

这次冒烟测试已经证明融合链路能够把 Vector 排到第 7 的 `B2` 拉回 Top-3，但这还不是
Hybrid 整体优于单路检索的结论。整体结论必须留到 Step 14.2，用全部 15 条查询统一评测。

### Step 14.2 🎯 评测 Hybrid · 已完成

**本步目标**：在完全相同的实验条件下比较 BM25、Vector、Hybrid，判断 RRF 是否真的利用
了两路检索器的互补性，而不是只凭 Q6 的单条冒烟结果下结论。

用完全相同的 23 篇语料、15 条 golden、V4 query 和 `k=3`，输出：

```text
BM25 V4 vs Vector vs Hybrid
```

逐条回答：

1. 哪些查询由 Vector 救回？
2. 哪些查询由 BM25 保住？
3. Hybrid 是否同时保住两类优势？
4. Q2/Q3 的零正例问题是否仍存在？

#### 原子步骤

1. 创建独立入口 `hybrid_eval.py`；
2. 加载一次 corpus 和 golden；
3. 创建 BM25、Vector、Hybrid 三个检索器；
4. 三路都使用 `v4_your_strategy()` 和 `k=3`；
5. 先打印三路整体 Recall、Precision、MRR；
6. 再逐查询打印 expected 和三路 Top-3；
7. 分别比较 Hybrid 相对 BM25、相对 Vector 是改善、持平、退化还是混合；
8. 最后单独分析 Q1、Q6、Q2/Q3/Q15，不调整 RRF 参数。

#### 代码阅读级别

**🔴 必须逐行读懂**：

- 为什么三个检索器必须共用同一个 query builder；
- `compare()` 如何根据三项指标判断改善、退化和混合；
- 为什么必须输出逐查询结果，不能只看三个平均数；
- 为什么本轮禁止根据结果立即调 `candidate_k` 或 `rank_constant`。

**🟡 理解协议和效果即可**：

- 汇总表与逐查询表的字符串格式化；
- JSON 读取和字典索引。

**⚪ 本步不用深入**：

- Ollama HTTP 请求细节；
- 文档向量缓存的序列化实现；
- Reranker 和弃权阈值设计。

**最终验收**：能指出具体 query_id 和文档 ID，并用检索机制解释结果。
如果 Hybrid 没有超过最佳单路，也要保留结果并分析原因，不能为了得到好看分数调到过拟合。

2026-09-30 实测结果：

```text
Retriever   Recall   Precision   MRR
BM25 V4     0.7733   0.3778      0.8000
Vector      0.7400   0.3556      0.8000
Hybrid RRF  0.7733   0.3778      0.8000

Hybrid vs BM25：改善 0 | 退化 0 | 持平 15 | 混合 0
Hybrid vs Vector：改善 1 | 退化 0 | 持平 14 | 混合 0
```

#### 逐类结论

**Q6：BM25 成功补回 Vector 的漏召回**

```text
BM25   → ['E2', 'B2', 'E1']
Vector → ['E2', 'C1', 'H3']
Hybrid → ['E2', 'H2', 'B2']
```

Vector 中 `B2` 排第 7，但 BM25 把它排第 2。RRF 累加两路排名贡献后，`B2` 回到第 3，
因此 Hybrid 相对 Vector 的 Recall 从 `0.5` 恢复到 `1.0`。这证明 BM25 的精确术语匹配
能够保护 Vector 因整篇文档语义稀释而漏掉的结果。

**Q1：没有出现 Vector 独立救回 BM25 的 Top-3 案例**

```text
BM25   → ['C1', 'H3', 'H2']
Vector → ['C1', 'H1', 'H3']
Hybrid → ['C1', 'H3', 'H1']
```

三路 Top-3 都是正例，所以 Recall、Precision、RR 全部持平。Vector 虽然提升了行业黑话
文档 `C2` 的完整排名，但它没有进入 Top-3；RRF 因而没有在当前指标中体现语义召回收益。

**Q2/Q3/Q15：Hybrid 仍然不会弃权**

三条查询的 golden 都是 `[]`，但 Hybrid 仍返回三篇文档。原因是 RRF 只重新组合两路排名，
不会判断候选是否达到最低相关性。若 BM25 和 Vector 都在“硬选最近的文档”，RRF 也只能
在这些候选中继续排序，不能自动得出“知识库中没有答案”。

**其他查询：指标全部持平，但返回的负例可能发生变化**

例如 Q14 中：

```text
BM25   → ['B2', 'E3', 'C1']
Vector → ['E3', 'B2', 'H3']
Hybrid → ['B2', 'E3', 'C1']
```

`B2/E3` 都是正例，所以三路 Recall 和 Precision 相同。RRF 中 `B2` 与 `E3` 分别是两路的
第 1/2 名和第 2/1 名，总分相同，最终由 `doc_id` 升序规则让 `B2` 排在前面。这说明稳定
排序规则可能决定同分文档的最终先后，但不会改变本条查询的指标。

#### 本步最终判断

当前实验只能证明：

```text
Hybrid 成功消除了 Vector 在 Q6 上的退化；
Hybrid 达到了当前更强单路 BM25 的整体水平；
Hybrid 没有超过 BM25，也没有解决零正例弃权；
当前数据尚未出现“Vector 独立救回 BM25 Top-3 失败”的案例。
```

因此不能把结果描述成“Hybrid 全面提升了检索效果”。更准确的表达是：

> RRF 在不降低当前 BM25 指标的情况下，利用 BM25 排名修复了 Vector 的一个失败案例，
> 表现为一种稳定性保护；但由于当前测试集没有 Vector 独立救回 BM25 的 Top-3 案例，
> 尚不能充分证明双向互补收益。

**面试核心认知**：

1. 融合系统的价值不一定表现为超过最强单路，也可能表现为降低单路模型的失败风险；
2. “Hybrid 等于 BM25”不代表 RRF 没工作，而可能是 BM25 本来就是当前数据上的最强单路；
3. 只有逐查询分析，才能发现 Q6 被救回，平均分只会告诉我们 Hybrid 最终追平了 BM25；
4. RRF 只能融合已经召回的候选，不能解决两路都漏召回或无答案弃权；
5. 当前 15 条是开发集，不能为了制造 Hybrid 提升而立即调参，下一步应冻结实现并扩充独立测试集。

#### 面试版总结

> 我实现了 BM25 与向量检索的 RRF 融合，并在相同语料、相同 V4 query、相同 `k=3`
> 的条件下进行了对照评测。BM25 的 Recall@3 为 `0.7733`，Vector 为 `0.7400`，Hybrid
> 为 `0.7733`。Hybrid 没有超过最强单路 BM25，但成功修复了 Vector 在 Q6 上的漏召回：
> `B2` 因为是多主题长文档，在单向量表示中从 BM25 第 2 降到 Vector 第 7；RRF 利用
> BM25 的精确术语排名，将它重新带回 Top-3。另一方面，Vector 虽然把行业黑话文档
> `C2` 从 BM25 第 9 提升到第 5，但没有跨过 Top-3，因此平均指标没有体现这次排名改善。
> 这说明 BM25 擅长精确词面，Vector 擅长语义改写，RRF 可以降低单路检索的失败风险，
> 但不能凭空召回两路都没找到的文档，也不能解决无答案查询的弃权问题。下一步应冻结
> 当前参数，在独立测试集上验证双向互补性，并单独设计相关性阈值或 reranker 处理弃权。

一句话版本：

> **RRF 本次没有提高最优平均分，但在不损伤 BM25 的前提下修复了 Vector 的具体失败，
> 证明了融合的稳定性价值；是否具有普遍增益，还需要独立测试集验证。**

#### 逐项结论

**1. 三路 Recall 与 Precision 完全相同。**

- T01～T12 的单正例都进入了三路 Top-3；
- T13/T14 是零正例，但三路都返回了三篇文档，因此 Recall 和 Precision 都是 0；
- T15 有 4 篇正例，而 `top_k=3` 最多只能返回 3 篇，所以三路 Recall 上限都是 `3/4=0.75`；
- T15 三路返回的 3 篇全部是正例，因此 Precision 都是 1.0。

因此 T15 的 `recall=0.75` 不是检索器把负例排进来了，而是评测口径本身存在 Top-3 容量
上限。冻结评测结束后不能为这份 holdout 临时把 `k` 改成 4；未来可在新测试集同时报告
Recall@3 与 Recall@5，或补充 nDCG 等排序指标。

**2. Hybrid 只在 T01 改善了首位排序，因此只提高 MRR。**

```text
T01 expected = ['C2']
BM25          = ['F3', 'C2', 'G2']  RR=0.5
Vector        = ['H3', 'C2', 'H1']  RR=0.5
Hybrid        = ['C2', 'H3', 'F3']  RR=1.0
```

`C2` 在 BM25 和 Vector 中都排第 2，是两路都稳定认可的候选；BM25 的第 1 名 `F3` 是
金融信贷比价，主要受到“综合比较、成本”等词面吸引，Vector 的第 1 名 `H3` 是采购询价
比价，业务领域接近但缺少 should-cost/TCO 式合理成本判断。RRF 不直接理解业务语义，
但会奖励“两路排名都靠前”的共识，因此把 `C2` 提升到第 1。

这个案例证明的是**共识排序收益**，不是 Vector 独立发现了 BM25 完全漏掉的正例：`C2`
原本已经在两路 Top-3 中，所以 Recall 和 Precision 不变，只有第一正例的位置改善。

**3. 没有出现 Vector-only rescue，也没有出现 BM25-only protection。**

按“某一路 Top-3 至少命中一个正例、另一路完全未命中”的口径统计，两类案例都是 0。
这意味着本测试集没有提供新的双向互补证据。当前能确认的仍然是：

```text
BM25 与 Vector 对这批有答案查询都能找到正例；
Hybrid 能利用两路共识改善个别正例的首位排序；
但 Hybrid 没有提高 Recall@3 或 Precision@3。
```

**4. T13/T14 再次确认三路都没有弃权能力。**

```text
T13 视觉缺陷检测：
BM25   → ['I2', 'I4', 'I1']
Vector → ['I2', 'H3', 'C1']
Hybrid → ['I2', 'H3', 'F2']

T14 需求预测与生产排程：
BM25   → ['I2', 'B2', 'I4']
Vector → ['H3', 'E3', 'C2']
Hybrid → ['H3', 'I4', 'I2']
```

T13 中，`I2` 含“检测、缺陷、自动、识别”等表面相关词，因此 BM25 和 Vector 都把它
当成最近候选，但它检测的是代码缺陷，不是产线产品外观；`I1/I4` 受到“识别、检测、图片、
自动”等泛化能力词影响；`H3/C1/F2` 则共享“自动检查、识别、解析、异常”等流程语义。
这些文档只是局部概念相似，都不能完成相机视觉质检。

T14 中，BM25 被“计划、管理、自动、流程”等泛词吸引；Vector 更容易找到“历史数据、趋势、
预测、计划、推荐”等抽象流程相似的采购文档 `H3/E3/C2`。但语义相似度只能回答“谁最像”，
不能自动判断“最像的也不够相关”。RRF 又只融合两路名次，所以同样无法输出空列表。

这两个案例把下一阶段问题界定得很清楚：**缺少的不是第三种召回排序，而是候选相关性判定
与 no-answer 阈值。** 可以考虑 cross-encoder/LLM reranker、相似度校准或单独的可回答性
分类器，但必须在新的开发集上设计，不能继续使用本 holdout 调参。

**5. T15 展示的是不同技术路线之间的正例替换。**

```text
BM25   → ['C1', 'H2', 'H3']
Vector → ['C1', 'H1', 'H3']
Hybrid → ['C1', 'H2', 'H3']
```

三组结果都没有负例。BM25/Hybrid 更偏向包含“多模态、语义对齐、字段抽取”的 `H2`，
Vector 选择了描述“上传报价文件、自动识别、物料对齐”的轻量 SaaS `H1`。这不是退化，
而是 `top_k=3` 无法同时容纳 4 篇完整正例。

#### 最终判断

本次 holdout 支持以下结论：

1. V4、BM25 和 Vector 对新的有答案查询表达具有一定稳定性，T01～T12 都成功召回正例；
2. Hybrid 没有提高 Recall@3/Precision@3，但通过两路共识把 T01 正例从第 2 提到第 1，
   MRR 从 `0.8333` 提升到 `0.8667`；
3. 没有观察到 Vector-only rescue 或 BM25-only protection，双向互补性仍未被充分证明；
4. 三路在 T13/T14 都错误地硬返回候选，零正例弃权是当前最明确的能力缺口；
5. T15 暴露了多正例数量大于 `top_k` 时 Recall 的结构性上限，解读指标时必须结合正例数；
6. holdout 分数高于开发集不代表算法经过本步“变强”，因为代码未变化、两组查询难度不同，
   不能直接把跨数据集分数差当作模型提升。

#### 数据限制

- 查询与标签均由助手按用户要求创建，评测者并不独立；
- 仍使用原 23 篇语料，只验证新查询表达，不验证新文档和新业务领域；
- T01～T12 大多存在明确业务术语，可能使测试集整体偏容易；
- 本次结果只可作为冻结回归证据，不应包装成统计显著或生产级效果证明。

面试版总结：

> 我在冻结 V4、Top-3、qwen3-embedding:0.6b、RRF candidate_k=10 和常数 60 后，

> Recall@3 都是 0.85，Precision@3 都是 0.3333；Hybrid 没有增加召回，但通过 RRF

# 附录 · 诊断证据（已完成，供回溯）

## A. 为什么 recall@5 = 1.0 是假指标

脚手架原本那句提示：

> 分数很高（>0.8）→ 你的语料和查询用了同样的词，测不出语义鸿沟，**重做语料**

**这句诊断是错的（是我写错的），不要照做。** 你的语料其实是合格的。

证据：`corpus/solutions.json` 里 C1 的 metadata 自己就写了
`"词汇刻意避开客户口语（不出现『太慢』『耗时间』『遗漏』），用于测试语义鸿沟"`。
归因脚本也证实 C1 的得分构成里**没有**这些客户口语，两边词面确实不重叠。语义鸿沟你造出来了。

真因是两个纯机械缺陷：

**缺陷 1：k=5，语料只有 6 篇。**
recall@5 在 6 篇语料上是恒真指标。任意检索器只要返回 5 篇，
唯一那篇正例 C1 必然落在里面——除非它精确地把 C1 排到第 6 名。
这个 1.0 测的是「语料规模」，不是「检索能力」，信息量为零。

**缺陷 2：只看 recall，不看 precision。**
recall 只惩罚「漏」，完全不惩罚「滥」。
一个把 6 篇全部召回的检索器 recall 永远是 1.0，但它毫无用处——
真实 RAG 里这意味着 Context 被噪声塞满，token 预算浪费，生成质量下降。

## B. 已做的修复

| 改动 | 位置 | 说明 |
| --- | --- | --- |
| `TOP_K` 5 → 2 | `retrieval.py:35` | 让指标恢复判别力；语料够了以后 Step 6 改回 3 |
| 新增 `precision_at_k` | `retrieval.py:218` | **主指标**，暴露噪声 |
| 新增 `reciprocal_rank` / MRR | `retrieval.py:232` | 衡量排序质量 |
| 新增防呆断言 | `evaluate()` `:241` | `n_docs <= k*2` 时抛 `ValueError`，恒满分口径再也跑不出来 |
| `evaluate(query_builder=...)` | `retrieval.py:241` | 支持注入策略，消融实验依赖此参数 |
| 新增 `ablation.py` | 新文件 | 四种 query 构造策略对照 |

修复后基线：

```
mean recall@2    = 1.0
mean precision@2 = 0.5   ← 真实水平在这里
MRR              = 1.0
Q1: 期望=['C1'] 实际=['C1', 'C2']
```

## C. 归因：C1 排第一靠的是高频单字

C1 总分 58.5，贡献最高的 token：

```
   1.33  '段'      在C1出现2次
   1.33  '报价'    在C1出现2次
   1.33  '报'      在C1出现2次
   1.33  '异'      在C1出现2次
   1.33  '字段'    在C1出现2次
   1.33  '一'      在C1出现2次
   1.13  '的'      在C1出现3次
   1.13  '比'      在C1出现3次
   1.13  '与'      在C1出现3次
   1.06  '价'      在C1出现6次
   0.89  '比价'    在C1出现2次
```

注意 `'段'` `'一'` `'的'` `'与'`——无语义的单字/虚词，却贡献了最高分。
原因是 `tokenize` 同时产出 unigram 和 bigram，unigram 让**所有中文文档互相沾边**，
IDF 在小语料上又区分不开。

另一个发现：query 里 `"unknown"` 出现了 **6 次**（constraints 的五个 unknown + industry）。
BM25 把它当普通检索词，去匹配所有含 unknown 的文档。这是噪声自己匹配自己。
V1 剔掉它分数没变——又一次证明装置分辨不出差异。

你亲手经历了一次**评测装置失效**：

指标满分 → 第一反应是「我做得好」或「语料有问题」→ 两个都错 → 真因是指标本身没有判别力。

这就是 Evaluation 模块的核心教训，和你 Circle 1 得出的
「测试通过只证明设计的用例被验证成功，不能说明用例完整覆盖了任务功能」
是同一件事的两个面。
